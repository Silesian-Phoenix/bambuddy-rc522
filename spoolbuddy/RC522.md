# SpoolBuddy z RC522 na Raspberry Pi 5

Ten fork dodaje wybór czytnika w pliku `.env`. Nie zmienia frontendu ani API
Bambuddy. Bambuddy może pozostać na osobnym komputerze.

**Status: wersja do testów sprzętowych.** Testy automatyczne używają atrap SPI/GPIO.
Nie potwierdzają zasięgu anteny, okablowania ani odczytu/zapisu rzeczywistych tagów.

## Wybór czytnika

Usługa systemd wczytuje `/opt/bambuddy/spoolbuddy/.env` przy starcie.
Brak `SPOOLBUDDY_NFC_READER` oznacza dotychczasowy PN5180. Dla RC522 dodaj:

```ini
SPOOLBUDDY_NFC_READER=rc522
SPOOLBUDDY_NFC_SPI_BUS=0
SPOOLBUDDY_NFC_SPI_DEVICE=0
SPOOLBUDDY_NFC_SPI_SPEED_HZ=500000
SPOOLBUDDY_NFC_RST_PIN=25
```

Nie zastępuj całego pliku: zachowaj adres Bambuddy, klucz API i pozostałe ustawienia.
Nie dodawaj `.env` do Git. Nieznana nazwa czytnika kończy start wyraźnym błędem,
zamiast uruchamiać inny sterownik. `mfrc522` jest aliasem `rc522`.

RC522 używa **sprzętowego CS**, nie ręcznego GPIO23. Usuń ewentualne
`SPOOLBUDDY_NFC_NSS_PIN` z profilu RC522; sterownik odrzuca to nieobsługiwane
ustawienie. Numery GPIO w konfiguracji oznaczają BCM, nie numery fizycznych pinów.

## Okablowanie odpowiadające powyższemu profilowi

To proponowane połączenia, nie potwierdzenie istniejących przewodów.
Przepinaj przewody przy odłączonym zasilaniu Pi.

| RC522 | Raspberry Pi 5 |
|---|---|
| 3.3V | 3,3 V, fizyczny pin 1 |
| GND | masa, fizyczny pin 6 |
| SCK | GPIO11, pin 23 |
| MISO | GPIO9, pin 21 |
| MOSI | GPIO10, pin 19 |
| SDA / SS | GPIO8 / CE0, pin 24 |
| RST | GPIO25, pin 22 |
| IRQ | niepodłączony |

**Nie podłączaj RC522 do 5 V.** Oznaczenie SDA na module oznacza tutaj CS dla SPI,
nie linię I2C. Przy CE1 użyj GPIO7/pinu 26 i `SPOOLBUDDY_NFC_SPI_DEVICE=1`.

W `/boot/firmware/config.txt` potrzebne jest `dtparam=spi=on`. Dla tego profilu
RC522 nie może być aktywnego `dtoverlay=spi0-0cs`. Zmiana konfiguracji boot wymaga
restartu Pi. Zmiana samego `.env` wymaga restartu usługi, nie całego systemu.

## Diagnostyka po wdrożeniu kodu

Nie uruchamiaj drugiego sterownika równolegle z usługą: mogłyby zajmować te same
GPIO albo wysyłać komendy do wspólnej magistrali. Przy ręcznych testach:

```bash
sudo systemctl stop spoolbuddy
sudo -u spoolbuddy /opt/bambuddy/spoolbuddy/venv/bin/python \
  /opt/bambuddy/spoolbuddy/scripts/mfrc522_diag.py
sudo -u spoolbuddy /opt/bambuddy/spoolbuddy/venv/bin/python \
  /opt/bambuddy/spoolbuddy/scripts/mfrc522_diag.py --require-tag --timeout 10
sudo systemctl start spoolbuddy
```

Skrypt wczytuje wyłącznie ustawienia NFC z `.env`, bez wykonywania jego treści
i bez drukowania klucza API. Kod 0 oznacza udany test, 1 błąd, 2 brak tagu przed
upływem czasu. Test bez `--require-tag` sprawdza komunikację z czytnikiem.
Po nieudanym poleceniu również uruchom ponownie usługę. Zachowano nazwę
`mfrc522_spi_check.py` jako alias diagnostyki.

Istniejące polecenia diagnostyczne z Bambuddy wybierają właściwy skrypt po stronie
demona. Nic nie trzeba dodawać do frontendu.

## Tagi i ograniczenia

- Identyfikacja obsługuje kaskady UID 4/7/10 bajtów. Przykładaj jeden tag naraz;
  kolizje są odrzucane, a nie rozstrzygane.
- UID działa niezależnie od powodzenia odczytu metadanych Bambu. Odczyt danych
  Bambu jest zaimplementowany, ale wymaga prób z rzeczywistymi szpulami.
- Zapis jest ograniczony do rozpoznanych NTAG213/215/216 z prawidłowym GET_VERSION
  i zapisywalnym Capability Container. Inne tagi mogą być identyfikowane po UID,
  ale zapis zostanie odrzucony.
- Sprawdzane są CRC, ACK, granice obszaru NDEF oraz odczyt danych po zapisie.
  Kod nie zapisuje UID, CC, stron blokad ani haseł. Klony o innych odpowiedziach
  wersji mogą zostać odrzucone.
- Zapis wielu stron nie jest atomowy. Wyjęcie tagu lub blokada pamięci w trakcie
  operacji może pozostawić częściowe dane; błąd nie jest raportowany jako sukces.

Implementacja protokołu opiera się na dokumentacji
[MFRC522](https://www.nxp.com/docs/en/data-sheet/MFRC522.pdf) i
[NTAG213/215/216](https://www.nxp.com/docs/en/data-sheet/NTAG213_215_216.pdf).

## Instalator i aktualizacje

Instalator forka ma opcję `--nfc-reader rc522`. Bez niej zachowuje zapisany wybór
z `.env`, a przy pierwszej instalacji wybiera PN5180. Dla RC522 wyłącza overlay
`spi0-0cs` i zachowuje dotychczasowe ustawienia pinów przy ponownej instalacji.
Zmiana czytnika wymaga sprawdzenia, czy zachowane piny odpowiadają nowemu modułowi.
Nie używaj ponownej instalacji jako zwykłej aktualizacji istniejącego kiosku.

Docelowo `origin` na Pi powinien wskazywać `Silesian-Phoenix/bambuddy-rc522`,
a poprawki muszą być commitami na wdrażanej gałęzi. Oficjalny projekt dodajemy
osobno jako `upstream`. Zmiany upstream najpierw scalamy i testujemy w forku.

**Nie używaj przycisku aktualizacji, dopóki nie sprawdzimy aktualizatora na PC.**
W analizowanej wersji Bambuddy wybiera swoją gałąź i wykonuje na Pi
`reset --hard origin/<gałąź>`. Testowa gałąź `feature/rc522` nie jest automatycznie
chroniona przed przełączeniem na `dev`. Docelowe scalenie do własnego `dev` oraz
zmiana `origin` to osobny etap wdrożenia. Sam fork nie aktualizuje się z upstream.

## Powrót do PN5180

Ustaw `SPOOLBUDDY_NFC_READER=pn5180`, przywróć właściwe przewody i konfigurację
SPI dla PN5180. Sprawdź ustawienia RST/BUSY/NSS: profil RC522 ma RST=25, podczas
gdy domyślny PN5180 ma RST=24, BUSY=25, NSS=23. Nie zostawiaj sprzecznych ustawień.

## Testy bez sprzętu

W katalogu repozytorium, w środowisku z pytest, pytest-asyncio i httpx:

```bash
PYTHONPATH=spoolbuddy python -m pytest spoolbuddy/tests
```

Testy instalatora uruchamiają wybrane funkcje Bash na plikach tymczasowych.
Pełny zestaw testów projektu wymaga Linuksa (FIFO, tryby plików). Na Windows
testy RC522, wyboru czytnika, demona i instalatora można uruchamiać osobno;
`BASH_EXE` pozwala wskazać Bash z Git for Windows.
